# Закрытая beta: изолированный пилот и общий invite-only вход

Разделы до «Новый общий invite-only вход» относятся к `scripts/closed_beta_bot.py`.
Общий бот описан отдельно ниже. Старый
`telegram_schedule_bot.py`, wrapper `telegram-bot`, n8n и инъекционный
`TelegramMultiUserDispatcher` не являются входом закрытого пилота.

## Минимальный допуск

До первого приглашения нужны все пять условий:

1. Локальный synthetic critical-path suite проходит.
2. На каждого студента выделены **свой Telegram-бот, один private chat ID,
   отдельный каталог состояния и отдельный Google OAuth token**. Один процесс
   на бота. Не использовать один bot token в нескольких процессах.
3. На выделенном тестовом аккаунте проверен путь ниже: onboarding → preview
   без записей → явное подтверждение → повтор → restart.
4. Backup тестового пользователя восстановлен в пустой каталог; состояние
   onboarding, источник, план и журнал Calendar сохранились.
5. Есть оператор, который останавливает процесс при неоднозначности, сохраняет
   backup и проверяет проблему без очистки журнала и без чужого аккаунта.

**Локальные проверки не подтверждают работоспособность реальных Telegram,
ТПУ или Google. `--check` проверяет только локальную конфигурацию.**
Базовая целевая команда пилота: **81 passed**; результат расширенной проверки
общего входа приведён в конце документа.
В ходе разработки live-сервисы и деплой не запускались.

Сначала используйте отдельного тестового бота, тестовый Google-аккаунт и
синтетический сценарий. Создайте бота вручную через BotFather; не публикуйте
ссылку. Получите private chat ID приглашённого участника доверенным способом.
Разрешение привязано к числовому ID, а не к username или possession ссылки.
Групповые сообщения, чужие отправители и неизвестные чаты игнорируются.

Для **каждого** экземпляра задайте переменные через защищённое окружение
процесса. Скрипт не читает `.env`. Не помещайте токены в историю команд,
репозиторий, логи или каталог состояния.

```text
TELEGRAM_BOT_TOKEN             = индивидуальный bot token из secret store
TELEGRAM_CHAT_ID               = private chat ID приглашённого студента
PERSONAL_OS_DATA_DIR           = абсолютный путь, например /srv/personalos/pilot-01/state
GOOGLE_CALENDAR_CREDENTIALS_PATH = абсолютный путь к OAuth client JSON вне state
GOOGLE_CALENDAR_TOKEN_PATH     = индивидуальный абсолютный путь вне state
```

Подготовьте приватные каталоги. Команды ниже выполняются **после** безопасной
загрузки этих переменных, не вставляйте секреты в текст команд:

```bash
umask 077
mkdir -p "$PERSONAL_OS_DATA_DIR"
chmod 700 "$PERSONAL_OS_DATA_DIR"
python3 scripts/authorize_google_calendar.py
chmod 600 "$GOOGLE_CALENDAR_TOKEN_PATH"
python3 scripts/closed_beta_bot.py --check
PYTHONDONTWRITEBYTECODE=1 python3 scripts/closed_beta_bot.py
```

OAuth — отдельное действие пользователя в браузере. Проверить выбранный
Google-аккаунт до согласия; никогда не выдавать студентам общий токен оператора.
В polling-процессе интерактивный OAuth отключён: при недействительной авторизации
планирование останавливается. Домен, webhook, n8n и платежи этому режиму не нужны.

Для длительного запуска используйте существующий supervisor с закрытым
окружением и постоянным приватным томом. Не запускайте старый бот параллельно.
Блокировка `.pilot.lock` предотвращает два экземпляра на одном state-каталоге.
Потеря процесса не удаляет state; обычный перезапуск использует тот же каталог.

## Проверка одного тестового аккаунта перед приглашениями

1. Чужой private chat и группа не получают доступа к состоянию. Разрешённый
   студент отправляет `/start`, выбирает часовой пояс.
2. `/connect_tpu <публичная ссылка группы>` → `/attendance` → ответы о занятиях.
   Источник проверяется заново по текущей академической неделе; экспорт не
   хранится в каталоге пользователя. Не использовать ссылку с экспортным ключом.
3. `/sleep 23:00 06:40`, `/travel 30`, `/calendar_status`.
   Проверка Google не должна создавать даже пустой календарь.
4. `/weekly_preview`: проверить пары и подготовки. **Ни одно событие или
   календарь ещё не создаются.** Отмена оставляет Calendar неизменным.
5. Получить новый preview и нажать «Подтвердить запись» в течение 10 минут.
   Только сейчас создаётся `Personal University Schedule`, пары и подготовки.
   Не должно быть другой рабочей интеграции с календарём такого же назначения.
6. Повторное нажатие старой кнопки ничего не делает. `/update_all` заново
   проверяет источник и показывает сохранённый план, без повторных записей.
7. Перезапустить процесс: старые кнопки недействительны; новый preview читает
   сохранённые операции. Сбой после части записей не повод очищать state:
   повторить preview и дать новое подтверждение, проверить отсутствие дублей.
8. Отозвать доступ на тестовом аккаунте / отключить сеть: результат не должен
   называться успешным. После восстановления доступа повторить проверку.
9. Переместить/удалить тестовое событие вручную, вызвать `/update_all`: бот не
   восстанавливает его автоматически. Оператор сверяет расхождение в Calendar.
10. Изменившийся TPU-источник или настройки после публикации блокируют дальнейшую
    запись и требуют оператора. В пилоте нет автоматической замены опубликованного
    плана и нет кнопки «очистить всё».

Отмечайте только результат проверки и категорию ошибки; не копируйте личное
расписание, OAuth, токены или сообщения в отчёты. Не проверять отказ записи на
аккаунте студента; локальный synthetic test уже моделирует частичный сбой.

## Backup/restore до расширения до 5–10 человек

Остановите экземпляр (Ctrl+C либо stop вашего supervisor) и убедитесь, что
процесс завершён. Не делайте backup параллельно с записью: архив не является
транзакцией нескольких изменяющихся файлов. Для opaque user ID, вычисленного
из **текущего** private chat ID:

```bash
PILOT_USER_ID="$(python3 -c 'import hashlib, os; print("user-" + hashlib.sha256(os.environ["TELEGRAM_CHAT_ID"].encode("ascii")).hexdigest()[:24])')"
# Подготовьте закрытый backup-каталог и задайте PILOT_ARCHIVE, например:
# PILOT_ARCHIVE=/protected-backups/pilot-01.zip
python3 scripts/user_state_backup.py --data-dir "$PERSONAL_OS_DATA_DIR" \
  --archive "$PILOT_ARCHIVE" backup "$PILOT_USER_ID"
PILOT_RESTORE_DIR="$(mktemp -d)"
python3 scripts/user_state_backup.py --data-dir "$PILOT_RESTORE_DIR" \
  --archive "$PILOT_ARCHIVE" restore "$PILOT_USER_ID"
```

Backup включает onboarding, публичный источник TPU, профиль, посещаемость,
reconciliation, операции и checkpoints Calendar. OAuth восстанавливается
отдельно через защищённое хранилище. Архив шифруется средствами хоста и не
передаётся другим пользователям. Восстановление поверх существующих файлов
запрещено. Реестр заново привяжет тот же chat ID к тому же opaque user ID.

Для проверки restored-экземпляра используйте тот же **тестовый** chat/token,
остановленный оригинальный процесс и `PERSONAL_OS_DATA_DIR="$PILOT_RESTORE_DIR"`.
Сначала `/start`, затем `/update_all`: onboarding и опубликованный план должны
сохраниться без дублирования событий. После проверки остановить restored-
экземпляр, вернуть исходный каталог и запустить только один процесс.

## Завтра: приглашения и ограничения

После успешного live-drill пригласите одного студента с сопровождением. Затем
повторите provisioning для остальных до 5–10. Если хотя бы один критерий
допуска не выполнен, приглашения пока не выдавать.

Ограничения: один пользователь на отдельного бота/процесс; ручной OAuth;
только учебный план TPU; опубликованный набор подготовок фиксируется.
Изменения источника, частично устаревший план, непоместившиеся подготовки,
неоднозначности и ручные расхождения требуют оператора. На следующую неделю
может потребоваться сопровождение; автоматического rollover нет. Не удаляйте
журналы, чтобы принудительно разблокировать пересчёт. Проекты, tutoring,
свободный текст, фоновые записи и административные команды старого бота в
этом входе отключены. Это сопровождаемый пилот, а не автономный сервис.

## Новый общий invite-only вход (локальный этап 23.09.2026)

`scripts/invited_beta_bot.py` — отдельный запускаемый polling-процесс для одного
бота и нескольких приглашённых private Telegram ID. Изолированный вход выше
сохранён; его данные автоматически не мигрируют. Новый вход использует тот же
`ClosedBetaApplication`: onboarding и первая подтверждаемая публикация работают,
и подтверждаемые добавления/переносы опубликованного плана доступны в общем
входе (см. раздел обновления ниже). Исчезнувшие/отменённые занятия удаляются только через отдельный разбор
`/review_missing`; ручные правки пока требуют оператора.
Пункты 3–5 продуктового развития в этот вход не добавлены.

Подготовьте новые каталоги вне репозитория, права 700, и защищённое окружение:

```text
TELEGRAM_BOT_TOKEN       = токен нового общего тестового бота
PERSONAL_OS_BETA_DIR     = /srv/personalos/beta
PERSONAL_OS_GOOGLE_DIR   = /srv/personalos/google
```

Скрипт не читает `.env`. `GOOGLE_CALENDAR_TOKEN_PATH` окружения при запуске
общего бота игнорируется: путь всегда вычисляется отдельно для пользователя.
Не запускайте другой polling-процесс с тем же bot token, даже с другим каталогом.

Оператор выдаёт/отзывает доступ числовому Telegram user ID:

```bash
umask 077
python3 scripts/invited_beta_bot.py invite 123456789
python3 scripts/invited_beta_bot.py check
PYTHONDONTWRITEBYTECODE=1 python3 scripts/invited_beta_bot.py run
# В другом терминале с тем же защищённым окружением:
python3 scripts/invited_beta_bot.py revoke 123456789
```

Неизвестный `/start`, группа, отправитель с другим ID и чужая кнопка не дают
доступа. Отзыв ждёт завершения уже начатой операции пользователя: **после возврата
команды revoke** новые команды и записи заблокированы. Он не отменяет уже
отправленный запрос Google. Повторное приглашение инвалидирует прежние
подтверждения. Ошибка провайдера одного участника не завершает polling остальных.
Обработка последовательная: медленный провайдер временно задерживает очередь;
параллельных фоновых записей нет.

Onboarding доступен ещё до provisioning Google. Для каждого участника отдельно
вычислите ID и выполните существующий операторский OAuth в браузере, проверив
Google-аккаунт участника:

```bash
BETA_CHAT_ID=123456789
BETA_USER_ID="$(python3 -c 'import hashlib, sys; print("user-" + hashlib.sha256(sys.argv[1].encode("ascii")).hexdigest()[:24])' "$BETA_CHAT_ID")"
# GOOGLE_CALENDAR_CREDENTIALS_PATH передаётся из защищённого окружения.
GOOGLE_CALENDAR_TOKEN_PATH="$PERSONAL_OS_GOOGLE_DIR/$BETA_USER_ID.json" \
  python3 scripts/authorize_google_calendar.py
chmod 600 "$PERSONAL_OS_GOOGLE_DIR/$BETA_USER_ID.json"
```

Путь участника: `/start` → выбор timezone → `/connect_tpu <публичная ссылка>` →
`/attendance` → `/sleep 23:00 06:40` → `/travel 30` → `/calendar_status` →
`/weekly_preview` → подтверждение. До подтверждения Calendar не записывается.
Отсутствующая/недействительная авторизация блокирует Calendar, интерактивный OAuth
в боте отключён. Участники не должны намеренно подключать один Google-аккаунт:
отдельные файлы авторизации не доказывают различие удалённых аккаунтов.

### Backup и восстановление общего входа

Остановите общий процесс **и операторские изменения приглашений**. Для полного
восстановления сохраните приватную копию всего `PERSONAL_OS_BETA_DIR` средствами
хоста: она включает общий `polling_offset.json` (в том числе отклонённые updates),
`access.json` (допуск и его поколение), `last_update.json`
(защиту от повторов), вложенные `state/users_registry.json` и
`state/users/<opaque-id>/` с onboarding, источником и журналами операций. OAuth
хранится и восстанавливается отдельно. Файлы `.pilot.lock` и `.access.lock` не
несут бизнес-состояния; блокировки освобождаются при остановке процесса.
Восстанавливайте в **новый пустой приватный каталог**, никогда поверх работающего.

Для выборочного domain backup используйте существующий инструмент:

```bash
python3 scripts/user_state_backup.py \
  --data-dir "$PERSONAL_OS_BETA_DIR/$BETA_USER_ID/state" \
  --archive "$BETA_ARCHIVE" backup "$BETA_USER_ID"
# RESTORED_BETA_DIR — новый приватный каталог.
python3 scripts/user_state_backup.py \
  --data-dir "$RESTORED_BETA_DIR/$BETA_USER_ID/state" \
  --archive "$BETA_ARCHIVE" restore "$BETA_USER_ID"
```

Этот ZIP сам по себе не включает приглашение и cursor: отдельно восстановите
`access.json` и `last_update.json` из той же остановленной копии в
`$RESTORED_BETA_DIR/$BETA_USER_ID/`. Для восстановления всего бота перенесите
также `polling_offset.json` в корень `$RESTORED_BETA_DIR` из той же копии.
Не сбрасывайте cursor для повторного исполнения
старых updates. После crash update мог быть принят без доставки ответа;
отправьте **новую** `/weekly_preview` и подтвердите восстановление операции.
Старые подтверждения после restart недействительны. Не очищайте журналы.

### Обновление опубликованного плана (общий бот, 24.09.2026)

Новые публикации общего бота сохраняют проверенный снимок событий Calendar в
существующем `draft_operations.json`. `/update_all` и `/weekly_preview` заново
читают источник, настройки и Calendar, затем показывают добавления и изменения:
название, старое/новое время, изменения места и описания. До нажатия
«Подтвердить обновление» удалённой записи нет. Кнопка действует 10 минут,
относится к конкретной версии и предложению, сбрасывается следующей командой
и перезапуском. Повтор без изменений не пишет Calendar.

Перед записью снова проверяются исходные данные, опубликованный снимок,
владение, Google ID, доступность времени и версии событий. Обновления существующих
событий используют условный PATCH с ETag: ручная правка между проверкой и записью
останавливает обновление. Пользовательские reminders не сбрасываются. Несколько
совпадений одного UID, отсутствие версии, ручное изменение или удаление вызывают
остановку; они не дают разрешения пересоздать/перезаписать событие.

В журнал сначала сохраняется неизменяемая цель обновления и намерение записи.
После частичного сбоя отправьте новую `/weekly_preview`: она покажет прежнюю
цель и предложит подтвердить продолжение. Уже выполненная точная запись
проверяется без повторной мутации. Если исходные данные успели измениться,
автоматическое продолжение остановится. Если исход попытки вставки неоднозначен
и события уже нет, система не отличает неудавшуюся вставку от последующего
ручного удаления — требуется оператор, событие не создаётся повторно.

Backup/restore выше включает опубликованный снимок и pending update внутри
`draft_operations.json`; версия формата файла остаётся 1, миграции не запускаются. Старые
операции без этих необязательных полей читаются, но обновление публикации без
доказуемого baseline блокируется. Не очищайте старые состояния ради перехода;
для live-проверки создайте нового тестового участника и новую публикацию.
Изолированный `closed_beta_bot.py` сохраняет прежнее поведение фиксированного плана.

Для ручного live-drill общего бота:

1. На выделенном аккаунте пройти onboarding и первую публикацию.
2. При изменении TPU-источника или настроек вызвать `/update_all`; сверить
   конкретные изменения и отсутствие записи до подтверждения.
3. Подтвердить: проверить перемещение тех же событий, отсутствие дублей;
   повторить `/update_all` и старую кнопку — новых записей быть не должно.
4. Получить preview, изменить настройки, проверить устаревшую кнопку.
5. На тестовом событии вручную изменить время/удалить его: новый preview
   должен остановить запись и сохранить ручное действие.
6. Проверить restart и восстановление из остановленной backup-копии на тестовом
   пользователе. Искусственную частичную ошибку Google моделируют только локальные
   тесты; не повреждайте журналы или данные студента для её воспроизведения.

### Разбор исчезнувших занятий и подтверждаемое удаление

Если пара исчезла из проверенного TPU-источника или явно отменена источником,
обычный `/update_all` / `/weekly_preview` остановится и предложит `/review_missing`.
Эта команда показывает конкретный список опубликованных пар и связанных с ними
подготовок: названия и время каждого события. Исчезновение само по себе не
доказывает отмену: кнопка «Оставить сейчас» отменяет текущее предложение без записи.
Она не создаёт постоянного исключения; следующая проверка снова покажет вопрос.

«Подтвердить удаление перечисленных» разрешает удаление только этого списка.
Кнопка ограничена десятью минутами, версией опубликованного плана, источником и
настройками. Проверка перед записью снова читает источник и весь опубликованный
Calendar, проверяет Google ID, содержимое, владение и ETag. Каждое удаление
использует условный DELETE. Ручная правка/удаление, неоднозначная замена или
отсутствие версии события останавливают операцию; пользовательские события
и произвольные исключения из нового расчёта не становятся целями удаления.

Начатое удаление сохраняется в прежнем `pending_plan_update` внутри
`draft_operations.json`. После ошибки или restart откройте **`/review_missing`**:
появится тот же список и предложение продолжить после новой проверки. Уже
удалённые события не удаляются повторно; принимается и tombstone
(`status=cancelled`) с тем же Google ID. Другой ID с тем же UID останавливает
продолжение. Если источник или настройки изменились после частичного удаления,
продолжение блокируется до разбора оператором. Backup/restore выше сохраняет
все необходимые данные; миграция не нужна.

После успешного удаления остальные события остаются на прежних местах.
`/weekly_preview` отдельно предложит пересчёт; он снова требует подтверждения.
Возвращение ранее удалённой пары в источник даёт предложение добавления,
а не автоматическое восстановление.

Для live-проверки на новом тестовом участнике при подтверждённом исчезновении
или отмене в TPU проверьте путь `/update_all` → `/review_missing` →
«Оставить сейчас» → новый `/review_missing` → подтверждение. Убедитесь, что
удалены только перечисленные пара и подготовки, а остальные события сохранены.
Искусственные отказы, crash и неоднозначные ответы провайдера покрываются
локальными synthetic-тестами; рабочие данные для такого drill не изменяйте.

Пункт 2 **частично завершён**: добавления, переносы и явно подтверждённое удаление
исчезнувших/отменённых пар с подготовками реализованы. Ручные конфликты, удаление
по иным основаниям, уже наступившие события, пустой/невалидный источник и переход
между неделями требуют отдельного решения. Изолированный pilot не получает
команду `/review_missing`. Реальные Telegram/TPU/Google, условные PATCH и DELETE
ещё требуют live-проверки пользователя; synthetic-результаты её не заменяют.

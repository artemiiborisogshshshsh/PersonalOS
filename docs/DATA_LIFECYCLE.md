# Жизненный цикл данных в Personal OS

Этот документ описывает, как данные движутся по системе Personal OS от их создания или получения до архивирования или удаления. Он охватывает все основные типы данных: знания (Obsidian), операционное состояние (SQLite), внешние календарные события и метаданные.

## Общие принципы жизненного цикла данных

1. **Явные этапы**: Жизненный цикл каждого типа данных делится на четко определенные этапы (создание, изменение, использование, архивирование, удаление).
2. **Отслеживание изменений**: Для критических данных сохраняется история изменений для аудита и возможности отката.
3. **Управление жизненным циклом**: Этические политики определяют, как долго данные хранятся и когда они архивируются или удаляются.
4. **Безопасность на каждом этапе**: На каждом этапе жизненного цикла применяются соответствующие меры безопасности (шифрование, контроль доступа).
5. **Резервное копирование**: Критические данные регулярно резервируются согласно политике резервного копирования.

## Жизненный цикл знаний (Obsidian vault)

### Этапы:
1. **Создание**: 
   - Пользователь создает новую заметку в Obsidian vault.
   - Personal OS может предлагать создание заметки на основе шаблона (например, для нового курса или концепции), но окончательное решение за пользователем.
2. **Изменение**:
   - Пользователь напрямую редактирует заметку в Obsidian.
   - Personal OS может добавлять метаданные (например, секции с информацией о подготовке и задачах) в конец заметки, но НЕ изменяет существующий пользовательский контент.
   - Добавление метаданных осуществляется с проверкой на дублирование (по UID или timestamps).
3. **Использование**:
   - Personal OS читает заметки для построения внутреннего индекса знаний (курсы, концепции, связи).
   - Индекс используется для предложения связанного материала при создании задач или требований подготовки.
   - Чтение осуществляется при запуске системы или по запросу пользователя; результаты кешируются для производительности.
4. **Архивирование**:
   - Пользователь может архивировать заметки в Obsidian (например, переместить в архивную папку).
   - Personal OS обнаруживает архивирование при следующем сканировании и удаляет связанные метаданные из своего индекса (или помечает их как архивные).
   - Архивированные знания все еще могут быть доступны для чтения, но не участвуют в активном предложении связанного материала.
5. **Удаление**:
   - Пользователь удаляет заметку в Obsidian.
   - Personal OS обнаруживает удаление при следующем сканировании и удаляет все связанные метаданные и ссылки из своего внутреннего состояния.
   - Удаление заметки не влияет на операционное состояние (задачи, блоки подготовки), но может привести к "осиротевшим" ссылкам, которые система обрабатывает gracefully (например, показывает предупреждение).

### Метаданные, добавленные Personal OS:
- Формат: Секции в конце заметки с уникальными маркерами.
- Содержание: 
  - Для блоков подготовки: UID, время начала/конца,.summary, статус.
  - Для задач: UID, описание, статус, приоритет.
- Управление: 
  - При обновлении Personal OS проверяет существование секции по UID.
  - Если секция существует и содержимое изменилось, она обновляется.
  - Если секция отсутствует, она создается.
  - Если пользователь удаляет секцию, Personal OS не пытается восстановить ее при следующем обновлении.

## Жизненный цикл операционного состояния (SQLite)

### Этапы:
1. **Создание**:
   - UniversitySession: Создается при синхронизации с внешним расписанием (парсинг ICS или вызов API университета).
   - PreparationRequirement: Создается доменным сервисом на основе UniversitySession и политики подготовки.
   - Task: Создается пользователем direttamente в приложении или через интеграцию (Telegram, веб-интерфейс).
   - ScheduleBlock: Создается планировщиком при генерации плана или пользователем ręcznie.
   - ExecutionRecord: Создается после выполнения работы (автоматически или через подтверждение пользователя).
2. **Изменение**:
   - UniversitySession: Обновляется при обнаружении изменений во внешнем расписании (изменение времени, типа, отмены).
     - Изменения отражаются в операционном состоянии; история изменений сохраняется для аудита.
   - PreparationRequirement: Обновляется при изменении оценки времени, статуса или связей.
     - Статус может изменяться автоматически (например, при планировании) или вручную пользователем.
   - Task: Обновляется пользователем (изменение описания, оценки, статуса, приоритета).
   - ScheduleBlock: Обновляется планировщиком (при перепланировке) или пользователем (перенос, изменение времени).
     - Важно: Обновление ScheduleBlock НЕ должно автоматически изменять связанное PreparationRequirement или Task.
   - ExecutionRecord: НЕ изменяется после создания (immutable fact). Для исправления создается новая запись.
3. **Использование**:
   - Данные используются для генерации планов, отправки напоминаний, отображения в пользовательском интерфейсе.
   - Чтение осуществляется через репозитории с соответствующими методами выбора (по ID, по статусу, по диапазону времени и т.д.).
4. **Архивирование**:
   - Выполненные задачи и блоки подготовки архивируются по окончании семестра или по правилу "старше X месяцев".
   - Архивированные данные перемещаются в отдельные таблицы или помечаются флагом archived.
   - Архивированные данные исключаются из активных запросов, но доступны для исторического анализа и отчетов.
5. **Удаление**:
   - Пользователь может удалять задачи, блоки подготовки и требования подготовки явно.
   - При удалении связанные ExecutionRecord остаются для истории (но могут быть отмечены как связанные с удаленной сущностью).
   - Автоматическое удаление старых данных выполняется согласно политике retention (например, удалять данные старше 2 лет).
   - Удаление 수행яется через репозитории с соответствующими методами (delete_by_id, delete_old_than).

### История изменений:
- Для аудита и отката реализована таблица изменений (change log) для основных сущностей.
- Каждая запись содержит: тип операции (create, update, delete), timestamp, пользователь (если применимо), изменения в формате JSON.
- История изменений используется для функциональности "откат на N шагов" и аудита изменений.

## Жизненный цикл внешних календарных событий (Google Calendar)

### Этапы:
1. **Создание внешних обязательств**:
   - Событие создается во внешнем календаре пользователем или внешней системой (например, университетским расписанием).
   - Personal OS НЕ участвует в этом создании напрямую.
2. **Добавление в Personal OS**:
   - PersonalOS обнаруживает новое событие при синхронизации с внешним календарем (чтение через Google Calendar API).
   - Событие проверяется на соответствие критериям (например, принадлежность группе 8И41 для университетских сессий).
   - Если событие считается фиксированным обязательством, оно сохраняется в операционном состоянии как UniversitySession (или как отдельная сущность FixedCommitment).
   - Событие помечается как прочитано и его iCalUID сохраняется для будущей идентификации.
3. **Изменение внешних обязательств**:
   - Пользователь или внешняя система изменяет событие во внешнем календаре (время, название, отмена).
   - При следующей синхронизации Personal OS обнаруживает изменение по iCalUID.
   - Изменения применяются к операционному состоянию (обновление времени сессии, отметка как отмененная и т.д.).
   - История изменений сохраняет информацию о внешнем изменении.
4. **Создание блоков подготовки и задач (прогноз)**:
   - Personal OS создает события во внешнем календаре как прогноз времени для блоков подготовки и задач.
   - Эти события создаются с особым маркером (например, в описании или как отдельный календарь) чтобы отличать их от внешних обязательств.
   - Уникальный iCalUID генерируется из внутреннего ID блока или задачи.
5. **Изменение прогнозных событий**:
   - Пользователь изменяет время или детали блока подготовки во внешнем календаре.
   - При следующей синхронизации Personal OS обнаруживает изменение.
   - В зависимости от политики доверия пользователю:
     - Если политика доверяет внешним изменениям: операционное состояние обновляется чтобы соответствовать внешнему календарю.
     - Если политика требует подтверждения: система помечает блок как требующий review и ожидает действия пользователя.
   - Внешнее изменение НЕ приводит к автоматическому удалению блока подготовки из операционного состояния без явной политики.
6. **Архивирование**:
   - Старые события во внешнем календаре остаются согласно политике хранения внешнего календаря (обычно бессрочно).
   - Personal OS может архивировать связанные записи в операционном состоянии (например, отмечать сессии как архивные после окончания семестра).
7. **Удаление**:
   - Пользователь удаляет событие во внешнем календаре.
   - При следующей синхронизации Personal OS обнаруживает отсутствие événements по ранее известному iCalUID.
   - Если событие было внешним обязательством: оно отмечается как удаленное в операционном состоянии (или удаляется после периода grace).
   - Если событие было прогнозным (блок подготовки/задача): операционное состояние может быть обновлено (пользователь намеренно удалил прогноз) или оставлено для review в зависимости от политики.
   - Personal OS НЕ удаляет события во внешнем календаре от своего имени (только читает и создает прогноз).

### Механизмы синхронизации:
- **iCalUID-based идентификация**: Каждое событие во внешнем календаре получает уникальный iCalUID при создании. Personal OS использует этот ID для отслеживания событий между синхронизациями.
- **Инкрементальная синхронизация**: При каждой синхронизации Personal OS запрашивает изменения с последней успешной синхронизации (используя токен изменения Google Calendar API) для эффективности.
- **Обработка конфликтов**: При обнаружении расхождения между внешним календарем и операционным состоянием система генерирует событие конфликта для review пользователем или применяет предопределенную политику.

## Жизненный цикл метаданных и конфигурации

### Конфигурация системы (файлы репозитория):
1. **Создание/Изменение**:
   - Пользователь изменяет файлы конфигурации (YAML/JSON) в репозитории.
   - Изменения отслеживаются системой контроля версий (Git).
2. **Использование**:
   - При запуске системы конфигурация читается из файлов.
   - Изменения вступают в силу после перезапуска соответствующих компонентов.
3. **Версионирование**:
   - Полная история изменений доступна через Git.
   - Возможность отката до предыдущих версий конфигурации.

### Метаданные в операционном состоянии:
1. **Создание**:
   - Генерируется автоматически системой (например, timestamps создания, версии схемы).
   - Добавляется при создании сущностей (но не изменяется при обновлении, кроме полей типа "updated_at").
2. **Использование**:
   - Используется для аудита, отладки, синхронизации.
   - Пример: timestamp последней модификации для обнаружения необходимости синхронизации с внешними системами.
3. **Архивирование/Удаление**:
   - Следует жизненному циклу связанной сущности.
   - Архивируется или удаляется вместе с сущностью, к которой относится.

## Политики хранения и архивирования

### Знания (Obsidian):
- **Хранение**: Бессрочно, пока пользователь не решит удалить или архивировать.
- **Архивирование**: По решению пользователя (ручное перемещение в архив).
- **Удаление**: По решению пользователя (удаление заметки).

### Операционное состояние (SQLite):
- **Активные данные**:
  - Текущий семестр: Все данные текущего семестра хранятся в активных таблицах.
  - Недавняя история: Данные за последние 6 месяцев для активного планирования и анализа.
- **Архивные данные**:
  - Данные старше 6 месяцев перемещаются в архивные таблицы или помечаются флагом.
  - Доступны для исторических отчетов и долгосрочного анализа.
- **Удаление**:
  - Данные старше 2 лет удаляются автоматически (политика можно настроить).
  - Исключение: данные, связанные с незавершенными задачами или важными вехами, могут быть сохранены дольше по решению пользователя.

### Внешние календарные события:
- **Внешний календарь**: Политика хранения определяется внешней системой (Google Calendar обычно хранит бессрочно).
- **Операционное состояние**:
  - Фиксированные обязательства: Хранятся до окончания события + grace period (например, 1 месяц после события).
  - Прогнозные события (блоки подготовки/задачи): Хранятся до выполнения или отмены задачи.

### Метаданные и файлы журналов:
- **Журналы событий**: Хранятся 3 месяца, затем архивируются или удаляются.
- **Журналы ошибок**: Хранятся 6 месяцев для анализа повторяющихся проблем.
- **Метрики производительности**: Хранятся 12 месяцев для dlouhodobého анализу.

## Обеспечение целостности на протяжении жизненного цикла

1. **Контроль версий схемы данных**:
   - Таблица версии схемы в SQLite отслеживает текущую версию.
   - Миграции применяются при запуске для обновления схемы без потери данных.
   - Обратная совместимость обеспечивается на уровне доступа к данным.

2. **Проверка целостности**:
   - Периодические проверки ссылочной целостности (foreign keys, уникальные ограничения).
   - Проверка на наличие "осиротевших" ссылок (например, ExecutionRecord без связанного PreparationRequirement).
   - Автоматическое исправление или уведомление пользователя в зависимости от серьезности.

3. **Резервное копирование**:
   - SQLite база данных резервируется ежедневно.
   - Резервные копии шифруются и хранятся в безопасном месте.
   - Политика хранения резервных копий: ежедневные за последнюю неделю, еженедельные за последний месяц, ежемесячные за последний год.

4. **Восстановление после сбоев**:
   - При запуске система проверяет целостность базы данных.
   - При обнаружении повреждения предлагает восстановить из последней известной хорошей резервной копии.
   - Журналы изменений (change log) используются для воспроизведения действий после восстановления.

## Особенности жизненного цикла для конкретных use cases

### Университетское расписание:
- **Сессия создана**: При обнаружении нового события в ICS или API университета.
- **Сессия изменена**: При обнаружении изменения времени, типа или отмены.
- **Сессия отменена**: 放置状态为cancelled, уведомление пользователю о необходимости перепланировки подготовки.
- **Сессия завершена**: После времени окончания сессия переходит в статус completed, готова к созданию записей выполнения если были блоки подготовки.

### Подготовка и задачи:
- **Требование подготовки создано**: При генерации на основе UniversitySession и политики подготовки.
- **Требование удовлетворено**: Когда связанный блок подготовки отмечен как completed.
- **Задача создана**: Пользователем или через интеграцию.
- **Задача выполнена**: Когда связанный блок выполнен или пользователь отмечает задачу как done.
- **Переназначение**: При изменении приоритета или дедлайна система предлагает перепланировать связанные блоки времени.

### Выполнение работы:
- **Запланировано**: Блок подготовки или задачи создан в статусе planned.
- **В процессе**: Пользователь начинает работу, блок переходит в статус in_progress.
- **Завершено**: Работа завершена, блок помечен как completed, создается ExecutionRecord.
- **Частично выполнено**: Пользователь указывает частичное выполнение, блок помечен как partially completed.
- **Пропущено**: Пользователь решает не выполнять работу, блок помечен как skipped, создается ExecutionRecord с результатом skipped.

## Резюм

Понимание жизненного цикла данных критично для:
- **Предсказуемости**: Пользователь знает, что происходит с данными на каждом этапе.
- **Эффективности ресурсов**: Данные архивируются или удаляются вовремя, не занимая ненужное место.
- **Соответствия требованиям**: Соблюдение политик retention и требований к аудиту.
- **Надежности**: Четко определенные этапы снижают риски потери данных или неконсистентности.
- **Доверия**: Пользователь видит, что система обрабатывает его данные ответственно на протяжении всего их жизненного цикла.

Персональная OS управляет жизненным циклом данных таким образом, чтобы знания сохранялись долгосрочно, операционное состояние оставалось актуальным и релевантным, а внешние интеграции работали предсказуемо и безопасно.

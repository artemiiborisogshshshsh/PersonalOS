# Данные и их источники истины в Personal OS

Это документ определяет, какой компонент системы является авторитетным источником истины (source of truth) для каждого типа данных в Personal OS.

## Принципы источника истины

1. **Единственный источник истины**: Для каждого типа данных должен быть определен один компонент, который является авторитетным источником. Все другие компоненты должны либо читать из этого источника, либо делегировать записи ему.
2. **Явные границы**: Источники истины и их границы должны быть明確но документированы.
3. **Минимальная дубликация**: Данные не должны дублироваться между компонентами без явной необходимости и механизма синхронизации.
4. **Явная синхронизация**: Любая репликация данных между источниками истины должна быть явной операцией с обработкой конфликтов.
5. **Последовательность**: При чтении данных из источника истины компоненты должны получать последовательное представление (хотя и не обязательно немедленно актуальное из-за задержек replication).

## Источники истины по типам данных

### 1. Знания и заметки (опциональная проекция)
- **Источник истины**: пользовательский vault только для пользовательского текста;
  operational сущности Personal OS не берут из него своё состояние.
- **Обоснование**: 
  - Obsidian предназначен для долгосрочного хранения и связывания знаний.
  - Пользователь непосредственно редактирует и связывает заметки, что делает его естественным местом для канонической информации.
  - Система может читать и добавлять метаданные, но не перезаписывать пользовательский контент.
- **Что хранится**:
  - Описания курсов, концепций, theorems, определений.
  - Решения задач, идеи, связи между концепциями.
  - Метаданные о подготовке и задачах (как отдельные секции, добавленные системой).
- **Что НЕ хранится**:
  - Временные состояния (расписание, текущие задачи).
  - Операционная информация (что запланировано на сегодня, выполнено ли что-то).

### 2. Операционное состояние (что запланировано, что выполнено, текущие оценки)
- **Источник истины**: SQLite база данных (или аналогичное хранилище операционного состояния)
- **Обоснование**:
  - Требует быстрых обновлений и сложных запросов (планирование, поиск по критериям).
  - Не подходит для хранения в виде простых файлов из-за необходимости транзакций и индексации.
  - Позволяет хранить историю изменений и выполнять анализ.
- **Что хранится**:
  - Задачи (Task) с их статусами, оценками, зависимостями.
  - Требования подготовки (PreparationRequirement) со статусами и оценками времени.
  - Запланированные блоки (ScheduleBlock) со статусами и привязками к задачам/требованиям.
  - Записи выполнения (ExecutionRecord) с фактическими временами и результатами.
  - Исторические данные для обучения оценок трудоемкости и предпочтений.
  - Текущие настройки пользователя (предпочтения времени, энергетические циклы и т.д.).
- **Что НЕ хранится**:
  - Долгосрочные знания (Это должно быть в Obsidian).
  - Внешние календарные события (Источник истины - внешний календарь, но мы читаем толькоFixed Commitments).
  - Временные файлы и кэши.

### 3. Google Calendar (availability input и projection)
- **Источник истины**: не является источником истины Personal OS.
- **Обоснование**:
  - Календарь используется для занятости и для показа пользователю проекции на устройствах.
  - Официальный TPU feed остаётся источником `UniversityEvent`; приложение хранит
    personal events, preparations, manual overrides и operations.
  - Personal OS читает занятость и пишет только принадлежащие ей прогнозы.
- **Что мы НЕ считаем источником истины (мы лишь читаем/проецируем)**:
  - Любые Calendar events не заменяют внутреннюю модель; они могут быть busy
    intervals или пользовательскими overrides, которые application layer явно
    фиксирует после проверки ownership.
  - Блоки подготовки и задачи, созданные Personal OS (это проекция нашего операционного состояния, но источник истины для них - наш SQLite).
  - Любые события, которые мы создаем, считаются лучшими усилиями по прогнозированию времени, но пользователь может их изменять или удалять во внешнем календаре без уведомления Personal OS (что приведет к несоответствию, которое мы должны обнаружить при следующей синхронизации).

### 4. Внешние задачи и напоминания (из Telegram, и т.д.)
- **Источник истины**: Внешняя система (Telegram,todo-приложения и т.д.)
- **Обоснование**:
  - Эти системы используются для коммуникации и быстрогоCapture идей.
  - Personal OS может интегрироваться для захвата задач, но не должен быть считаться источником истины для внешних систем.
- **Что хранится (что мы считаем источником истины)**:
  - Задачи, созданные пользователем в этих системах и импортированные в Personal OS.
- **Что мы НЕ считаем источником истины**:
  - Исходные задачи во внешней системе (мы только читаем их и храним копию в нашем операционном состоянии после явного импорта).

### 5. Временные журналы и метрики
- **Источник истины**: SQLite база данных (для структурированных данных) и файлы журналов (для неструктурированной отладки)
- **Обоснование**:
  - Структурированные метрики (количество выполненных задач, среднее отклонение оценок) удобно хранить в БД для запросов.
  - Неструктурированные журналы удобно хранить в файлах для последующего анализа.
- **Что хранится**:
  - Метрики производительности (в БД).
  - Журналы событий и ошибок (в файлах).

### 6. Конфигурация и настройки
- **Источник истины**: Файлы конфигурации в репозитории (YAML, JSON, TOML)
- **Обоснование**:
  - Настройки должны быть версиябельными и прозрачными.
  - Пользователь должен иметь возможность откатывать изменения и видеть историю.
- **Что хранится**:
  - Настройки планировщика (веса мягких ограничений, емкость дневной нагрузки).
  - Настройки интеграций (пути к файлам, учетные данные для внешних систем в зашифрованном виде).
  - Пользовательские предпочтения (которых нет в операционном состоянии, например, какие календари синхронизировать).

## Границы и协同工作 между источниками истины

### Между Obsidian (знания) и SQLite (операционное состояние)
- **Направление**: SQLite читает знания из Obsidian для контекста (например, при создании задачи система может предложить связанные концепции). Obsidian может получать метаданные от SQLite (например, секции с информацией о подготовке и задачах).
- **Механизм**: 
  - Чтение: При запуске или по запросу система сканирует Obsidian vault для построения внутреннего индекса знаний (кешированного для скорости). 
  - Запись: Система добавляет секции в конец заметок Obsidian (с уникальными идентификаторами, чтобы избежать дублирования) и никогда не修改 существующий пользовательский контент.
  - Конфликты: Если пользователь удаляет секцию, добавленную системой, при следующем обновлении система не будет пытаться восстановить ее (чтобы уважать пользовательское удаление). Однако система может добавить новую секцию с обновленной информацией.

### Между SQLite (операционное состояние) и Google Calendar (внешний календарь)
- **Направление**: 
  - Чтение: Personal OS периодически читает внешний календарь для обновления фиксированных обязательств (встречи, сессии и т.д.).
  - Запись: Personal OS пишет блоки подготовки и задачи в отдельный календарь (или в основной с особым маркером) как прогноз времени.
- **Механизм**:
  - Чтение: Используем Google Calendar API для получения событий в диапазоне времени. Мы фильтруем события по источнику (например, только те, что созданы внешними системами или пользователем напрямую) чтобы избежать чтения собственных прогнозов (если они помечены особо). Альтернативно, мы можем читать все события и использовать iCalUID или другие маркеры для идентификации собственных событий.
  - Запись: При создании блока подготовки или задачи мы создаем событие во внешнем календаре с уникальным iCalUID (генерируемым из нашего внутреннего ID). При обновлении мы ищем существующее событие по iCalUID и обновляем его, либо создаем новое, если не найдено.
  - Конфликты: 
    - Если пользователь удаляет наше событие во внешнем календаре, мы обнаруживаем это при следующей синхронизации и отмечаем блок как требуемый перепланировки (или удаляем его из нашего состояния, если считаем, что пользователь намеренно удалил прогноз).
    - Если пользователь изменяет время нашего события во внешнем календаре, мы имеем выбор: либо принять изменение как пользовательское переопределение (и обновить наше операционное состояние), либо считать это конфликтом и спросить пользователя. Выбор зависит от политики: для блоков подготовки мы можем принимать изменение как пользовательское предпочтение, для фиксированных обязательств мы должны уважать внешнее изменение как источник истины.

### Между внешними системами (Telegram) и SQLite
- **Направление**: 
  - Чтение: Personal OS может принимать команды и задачи из Telegram (или других систем) через интеграцию.
  - Запись: Personal OS не пишет обратно в Telegram как источник истины для задач (хотя может отправлять уведомления и подтверждения).
- **Механизм**:
  - Чтение: Мы предоставляем интерфейс (бот, вебхук и т.д.) для получения сообщений. Распакованные задачи преобразуются в задачи в нашем операционном состоянии с пометкой о источнике.
  - Запись: Мы не пишем задачи обратно в Telegram. Для уведомлений об исполнении мы можем отправлять сообщения, но они не считаются источником истины для состояния задачи.

## Обработка конфликтов и синхронизация

### Принципы
1. **Источник истины побеждает**: При конфликте между источником истины и репликой источник истины считается правильным.
2. **Явное обнаружение конфликтов**: Система должна обнаруживать и сообщать о конфликтах, а не разрешать их неявно.
3. **Пользователь в петле**: Для значительных конфликтов система должна запрашивать у пользователя решение.
4. **Идемпоентность**: Операции синхронизации должны быть идемпотентными (повторное применение не меняет результат после первого успешного применения).

### Примеры стратегий разрешения конфликтов

#### Конфликт между Obsidian и SQLite (метаданные в заметках)
- **Ситуация**: Пользователь удалил секцию, добавленную системой, из заметки Obsidian.
- **Решение**: 
  - При следующем сканировании Obsidian система отмечает, что секция отсутствует.
  - Система не пытается восстановить удаленную секцию (чтобы уважать пользовательское удаление).
  - Если система считает, что информация все еще актуальна (например, на основе операционного состояния), она может добавить новую секцию с обновленным содержимым (но не ту же самую, чтобы не бороться с пользователем).

#### Конфликт между SQLite и Google Calendar (блок времени)
- **Ситуация**: Пользователь изменил время события, созданного Personal OS, во внешнем календаре.
- **Решение (вариант A - доверие пользователю)**:
  - При следующей синхронизации система обнаруживает, что iCalUID события во внешнем календаре соответствует нашему блоку, но время отличается.
  - Система принимает внешнее изменение как пользовательское переопределение и обновляет операционное состояние (время блока в SQLite) чтобы соответствовать внешнему календарю.
  - Система логирует это событие для обучения (возможно, пользователь систематически отклоняется от наших прогнозов).
- **Решение (вариант B - осторожность)**:
  - Система обнаруживает расхождение и помечает блок как требующий review.
  - При следующем взаимодействии с пользователем система предлагает принять変更外部 календаря или вернуться к予定ному времени.
  - Выбор зависит от настройки пользователя: доверять ли внешним изменениям или считать их ошибкой.

#### Конфликт между внешними задачами и SQLite (импорт задач)
- **Ситуация**: Пользователь импортирует задачу из Telegram, которая уже существует в Personal OS (по содержанию или внешнему ID).
- **Решение**:
  - Система использует внешний ID (если предоставлен) для дедубликации.
  - Если внешний ID отсутствует, система использует нечеткое соответствие по названию и описанию для обнаружения потенциальных дубликатов.
  - При обнаружении дубликата система предлагает пользователю объединить задачи или выбрать одну как авторитетную.

## Резюм

Ясное определение источников истины критично для:
- Избегания неопределенности и конфликтов в данных.
- Обеспечения целостности системы при интеграции с внешними системами.
- Позволения пользователю понимать, где данные можно изменять, а gdzie they are derived.
- Упрощения отладки и аудита (потому что вы знаете, где искать "истинное" значение).

Персональная ОС следует принципу: хранить знания там, где они принадлежат (Obsidian), операционное состояние там, где оно нуждается в szybkiej mutability и запросах (SQLite), а внешние календари и системы коммуникаций оставлять как источники истины для своих соответствующих данных, осуществляя только чтение и явную запись прогнозов или импорта.

Это разделение ответственности позволяет каждой части системы сосредоточиться на своей strengths и минимизирует риски несовместимости и потери данных.

# Границы интеграции в Personal OS

Этот документ определяет четкие границы ответственности между основными компонентами Personal OS и внешними системами. Он описывает, что каждый компонент должен и не должен делать, чтобы поддержать чистую архитектуру и избежать называемых "архитектурных ошибок", таких как смешивание уровней ответственности или premature inheritance.

## Основные компоненты системы

Personal OS состоит из следующих логических слоев и компонентов:

1. **Доменный слой (Domain Layer)** - содержит чистую бизнес-логику,独立 от инфраструктуры.
2. **Слой приложения (Application Layer)** - определяет логику выполнения бизнес-сценариев (use cases), оркерирует доменные объекты.
3. **Слой инфраструктуры (Infrastructure Layer)** - реализует детали взаимодействия с внешними системами (БД, внешние API, файловая система).
4. **Внешние системы** - Obsidian, Google Calendar, Telegram, файловая система (для заметок и конфигурации).

Кроме того, внутри доменного слоя выделяем ключевые концепции (сущности, value objects, сервисы).

## Grenzen между слоями

### Доменный слой ↔ Слой приложения
- **Доменный слой** НЕ знает о слое приложения. Он содержит только pure business logic и правила.
- **Слой приложения** вызывает доменный слой для выполнения операций, но НЕ содержит бизнес-правил, которые должны быть в домене.
- **Пример**: 
  - Домен: `UniversitySession`, `PreparationRequirement`, `ScheduleBlock`, `ExecutionRecord` как классы с методами, отражающими бизнес-правила (например, `PreparationRequirement.calculate_effort()` based on session type и subject priority).
  - Приложение: Use case `GeneratePreparationBlocks` получает список `UniversitySession` из репозитория, для каждого создает `PreparationRequirement` через доменную фабрику, затем использует доменный сервис `Scheduler` для расчета оптимальных `ScheduleBlock`.

### Доменный слой ↔ Слой инфраструктуры
- **Доменный уровень** НЕ знает о слое инфраструктуры. Он работает с интерфейсами (портами), определенными в домене (например, `PreparationRequirementRepository`).
- **Слой инфраструктуры** реализует эти интерфейсы, используя конкретные технологии (SQLite, файлы и т.д.).
- **Запрет**: Доменные объекты НЕ должны содержать аннотации ORM, ссылаться на таблицы БД или знать о форматах внешних API.
- **Пример**: 
  - Доменный интерфейс: `interface UniversitySessionRepository { list_active_sessions(): List<UniversitySession>; }`
  - Инфраструктурная реализация: `class SqliteUniversitySessionRepository implements UniversitySessionRepository { ... }`
  - Доменные объекты (например, `UniversitySession`) содержат только данные и бизнес-методы, никаких ссылок на репозитории или БД.

### Слой приложения ↔ Слой инфраструктуры
- **Слой приложения** знает об инфраструктуре только через абстрактные интерфейсы (порты), определенные в слое приложения или доме.
- **Слой инfrastructure** реализует эти интерфейсы.
- **Пример**: 
  - Слой приложения определяет порт `interface CalendarGateway { sync_events(sessions: List<UniversitySession>): void; }`
  - Слой инфраструктуры предоставляет `class GoogleCalendarCalendarGateway implements CalendarGateway { ... }`, используя Google Calendar API.
  - Слой приложения использует этот порт в use case `SyncUniversitySchedule` без знания деталей реализации.

### Внутри доменного слоя: границы между концепциями

Четкое разделение обязанностей между доменными концепциями критично для избежания раздутых сущностей и смешивания ответственности.

#### UniversitySession
- **Ответственность**: Представляет фактическое учебное событие из внешнего источника (расписание университета).
- **Содержит**: 
  - Уникальный идентификатор (из внешнего источника, например, iCalUID).
  - Время начала и конца.
  - Тип события (лекция, лабораторная, práctica).
  - Предмет/курс.
  - Преподаватель (опционально).
  - Местоположение (опционально).
  - Сырой descripton из источника.
- **НЕ содержит**:
  - Любую информацию о подготовке (это компетенция `PreparationRequirement`).
  - Статус выполнения или планирования.
  - Ссылки на задачи или блоки подготовки (это создает двойную нарежку; связь устанавливается через сервисы или репозитории на уровне приложения).
- **Вариант**: Может быть value object, если не требуется идентичность вне контекста расписания, но обычно имеет ID для синхронизации с внешним источником.

#### PreparationRequirement
- **Ответственность**: Оценивает объем работы, необходимый для подготовки к конкретному `UniversitySession`. Это отдельная концепция от самого события.
- **Содержит**:
  - Ссылка на `UniversitySession` (по ID или как value object reference).
  - Оценка требуемого времени (в минутах) с указанием источника оценки (예: экспертная оценка, исторические данные) и уверенности в этой оценке.
  - Статус требования (например, `pending`, `in_progress`, `satisfied`).
  - Связь со студенческим материалом или концепциями (опционально, через ссылки на знания в Obsidian).
  - Дедлайн (по умолчанию - время начала сессии, но может быть ранее для сложных тем).
- **НЕ содержит**:
  - Информацию о том, когда конкретно будет выполнена подготовка (это компетенция `ScheduleBlock`).
  - Факт выполнения (это компетенция `ExecutionRecord`).
  - Логику планирования или распределения во времени (это компетенция `Scheduler`).
  - Ссылки на конкретные блоки времени в календаре.

#### ScheduleBlock
- **Ответственность**: Представляет зарезервированный блок времени в календаре для выполнения конкретной работы (подготовки или задачи).
- **Содержит**:
  - Уникальный идентификатор (внутри системы).
  - Ссылка на то, что делается (либо `PreparationRequirement.ID`, либо `Task.ID`).
  - Время начала и конца.
  - Статус блока (`planned`, `in_progress`, `completed`, `skipped`, `cancelled`).
  - Тип блока (`preparation`, `task`, `personal`, `fixed_commitment` для импортированных внешних обязательств).
  - Источник создания (`user_manual`, `system_generated`, `imported_from_calendar`).
- **НЕ содержит**:
  - Оценку требуемого времени (это属性 требования или задачи).
  - Факт выполнения работы (это запись в `ExecutionRecord`).
  - Логику, как этот блок был выбран среди альтернатив (это компетенция планировщика и использования scoring model).
  - Ссылки на знания в Obsidian (эта связь устанавливается через требование или задачу).

#### ExecutionRecord
- **Ответственность**: Фактографическая запись о том, что фактически произошло во время выполнения работы. Это immutable факт после записи.
- **Содержит**:
  - Уникальный идентификатор.
  - Ссылку на то, что должно было быть выполнено (либо `PreparationRequirement.ID`, либо `Task.ID`).
  - Факттическое время начала и конца выполнения.
  - Результат выполнения (`completed`, `partially_completed`, `skipped`).
  - Оценку усилий, затраченных на выполнение (в минутах) - для обучения улучшения будущих оценок.
  - Любые заметки о прерывках, причинах неполного выполнения и т.д.
  - Время создания записи (immutable).
- **НЕ содержит**:
  - Текущее состояние или статус, который может изменяться (это属性 требования или задачи).
  - Планы на будущее.
  - Логику перепланирования или обновления (это компетенция use case уровня приложения, например, `ReconcileExecution`).
  - MUTABLE поля после создания (запись считается immutable фактом; для исправления создается новая запись с пометкой о корректировке).

#### Task
- **Ответственность**: Представляет единицу работы, созданную пользователем для целей, не связанных напрямую с университетскими сессиями (проекты, преподавание, личные цели).
- **Содержит**:
  - Уникальный идентификатор.
  - Описание.
  - Связь с курсом, проектом или студенческим контекстом (опционально).
  - Оценка требуемого времени с источником и уверенностью.
  - Приоритет и сложность.
  - Дедлайн.
  - Статус (`todo`, `in_progress`, `done`).
- **НЕ содержит**:
  - Информацию о подготовке к университетским сессиям (это компетенция `PreparationRequirement`).
  - Факт выполнения (это компетенция `ExecutionRecord`).
  - Зарезервированные блоки времени (это компетенция `ScheduleBlock`).
  - Логику планирования во времени.

### Границы с внешними системами

#### Интеграция с Obsidian (знания)
- **Граница**: Personal OS читает заметки для построения индекса знаний и добавляет метаданные в конец заметок, НЕ изменяя существующий пользовательский контент.
- **Запрет**: 
  - Personal OS НЕ должен перезаписывать или модифицировать существующие разделы заметок, созданные пользователем.
  - Personal OS НЕ должен зависеть от структуры заметок для своей внутренней логики (например, парсить пользовательский контент для принятия решений).
- **Механизм интеграции**:
  - Чтение: Сканирование файлов `.md` в определенных директориях vault для извлечения канонической информации (курсы, концепции).
  - Запись: Добавление секций в конец заметки с уникальным маркером (например, `<!-- PersonalOS PreparationBlock: {uid} -->`) чтобы избежать дублирования и позволить безопасное удаление пользователем.

#### Интеграция с Google Calendar (время)
- **Граница**: 
  - Personal OS читает внешний календарь для извлечения фиксированных обязательств (университетские сессии, встречи) и считает их источником истины для времени обязательств.
  - Personal OS пишет блоки подготовки и задачи как прогноз времени в отдельный календарь (или в основной с особым тегом) и считает свой внутреннее состояние (SQLite) источником истины для этих блоков.
- **Запрет**:
  - Personal OS НЕ должен рассматривать внешний календарь как источник истины для блоков подготовки или задач, созданных системой.
  - Personal OS НЕ должен пытаться "синхронizовать" изменения внешнего календаря в свои блоки подготовки без явного пользовательского подтверждения (кроме случаев, когда политика явно доверяет внешним изменениям).
- **Механизм интеграции**:
  - Чтение: Получение событий через Google Calendar API, фильтрация по источнику (например, события не созданные Personal OS) чтобы определить фиксированные обязательства.
  - Запись: Создание/обновление событий во внешнем календаре с использованием уникального iCalUID, генерируемого из внутреннего ID блока Preparations или задачи. При конфликте ( External changed Personal OS block) применяется политика доверия пользователю (обновление внутреннего состояния) или требуется разрешение конфликта.
  - Источник истины для времени: 
    - Для фиксированных обязательств: внешний календарь.
    - Для блоков подготовки и задач: внутреннее состояние Personal OС (SQLite).

#### Интеграция с Telegram и другими системами ввода
- **Граница**: Personal OS может принимать команды и задачи из внешних систем ввода, но не считает их источником истины для состояния задач.
- **Запрет**:
  - Personal OS НЕ должен рассматривать внешние системы ввода как источник истины для состояния операционного состояния (SQLite).
  - Personal OS НЕ должен пытаться двухстороннюю синхронизацию состояния задач без явной необходимости и четкой политики разрешения конфликтов.
- **Механизм интеграции**:
  - Чтение: Предоставление интерфейса (бот, вебхук) для получения сообщений, преобразование их в задачи или команды в операционном состоянии с пометкой о источнике.
  - Запись: Отправка уведомлений и подтверждений обратно во внешнюю систему, но не запись состояния задач.

#### Хранение файлов (конфигурация, заметки, резервные копии)
- **Граница**: 
  - Конфигурация системы хранится в файлах репозитория (YAML/JSON) и считается источником истины для настроек.
  - Резервные копии операционного состояния могут храниться в файлах, но источник истины - SQLite.
- **Запрет**:
  - Personal OS НЕ должен хранить операционное состояние в обычных файлах как источник истины (из-за отсутствия транзакций и риска повреждения).
  - Personal OS НЕ должен зависеть от формата файлов заметок для своей логики (только для чтения знания и добавления метаданных).

## Особенные architectural запреты из обратной связи

Из последней обратной связи senior engineer выделены конкретные ошибки, которых следует избегать:

1. **ExecutionRecord не является доменной сущностью, которую нужно обновлять**:
   - ExecutionRecord - это immutable факт. Его НЕ следует обновлять после создания.
   - Для исправления ошибки в записи создается новая запись со ссылкой на предыдущую или с пометкой о корректировке.

2. **Подсчет PreparationRequirement должен быть отделен от UniversitySession**:
   - Не добавлять поля подготовки напрямую в UniversitySession.
   - PreparationRequirement - отдельная концепция, связанная с UniversitySession через reference, но не содержащаяся внутри него.

3. **Избегайте наследования там, где это возможно**:
   - Предпочтите композиция перед наследованием для передачи поведения.
   - Если наследование используется, оно должно соответствовать принципу подстановки Лисков.

4. **Reconciliation - это сервис/вариант использования, а не доменная сущность**:
   - Not create a `Reconciliation` entity in the domain.
   - Instead, have a use case/service `ReconcileExecutionService` that compares `ExecutionRecord` with `ScheduleBlock` and generates corrective actions.

5. **Dry Run - это режим выполнения на poziomie aplikacji, а не доменная концепция**:
   - Not add a `dry_run` flag to domain objects.
   - Instead, the application layer can invoke domain logic in a dry-run mode where side effects (like writing to infrastructure) are skipped or mocked.

6. **Горизонтальное расщепление: PlanCandidate vs WeeklyPlan**:
   - PlanCandidate - tentative plan, subject to change and scoring.
   - WeeklyPlan - committed plan that has been approved by the user and is the basis for execution.
   - They are distinct concepts; WeeklyPlan is not merely a subset of PlanCandidate.

7. **Ясные различия между концепциями**:
   - Requirement (abstract base or marker interface) -> PreparationRequirement (время, необходимое для подготовки к сессии) and Task (определенная пользователем работа).
   - ScheduleBlock - зарезервированный блок времени для выполнения чего-либо.
   - ExecutionRecord - фактическая запись о том, что произошло.

8. **Требования к REQUIREMENTS.md**:
   - Должен включать как функциональные, так и нефункциональные требования explícitно.
   - Не смешивать их или оставлятьimplicit.

9. **Источник расписания университета**:
   - Не полагаться на предварительно загруженный ICS-файл как источник истины.
   - Исследовать и документировать реальный источник официального расписания университета (например, API, регулярная загрузка с портала).

10. **DATA_OWNERSHIP.md и ADR-001**:
    - Эти документы должны быть созданы и рассматриваться перед любым кодом или инфраструктурой.

11. **Преждевременная схема SQLite**:
    - Не создавать схему БД до определения доменной модели и границ интеграции.
    - Схема БД - деталь инфраструктуры, которая должна следовать за доменом, а не руководить им.

12. **Отказ от Event Sourcing в начале**:
    - Не внедрять Event Sourcing как начальный подход к хранению состояния.
    - Использовать обычное хранение состояния с возможным добавлением журналов изменений для аудита позже.

13. **Избегайте преждевременного LSP**:
    - Не настраивать языковой сервер протокола (LSP) для Python на ранней стадии, если это не дает немедленной ценности.
    - Сосредоточьтесь на простоте и ясности кода сначала.

14. **Детерминированный планировщик**:
    - Планировщик должен быть детерминированным: при одинаковом входе одинаковый выход.
    - Это критично для предсказуемости и отладки.
    - Hard constraints (непересечение с фиксированными обязательствами) должны быть удовлетворены первыми.
    - Soft constraints (предпочтения времени, энергетические уровни) обрабатываются через взвешенную целевую функцию.

15. **AI не должно вызывать домен/репозиторий напрямую**:
    - При интеграции с внешними системами через AI (например, голосовые команды) AI должен interacting только с четко определенными прикладными слоем use cases, never directly accessing domain repositories or infrastructure.
    - Это предотвращает утечки abstraction и нарушение слоистости.

## Сводная таблица границ

| Компонент A          | Компонент B          | Тип границы                     | Направление основного потока | Запреты                                                                 |
|----------------------|----------------------|---------------------------------|------------------------------|-------------------------------------------------------------------------|
| Домен                | Приложение           | Use case вызывает домен         | Приложение → Домен           | Домен не знает о приложении; домен не содержит логики использования.    |
| Домен                | Инфраструктура       | Порты и адаптеры                | Инфраструктура реализует порты, определенные в доме или приложении | Домен не знает об инфраструктуре; нет аннотаций ORM в доменных объектах. |
| Приложение           | Инфраструктура       | Порты и адаптеры                | Приложение определяет порты, инфраструктура реализует | Приложение не знает деталей реализации инфраструктуры.                  |
| UniversitySession    | PreparationRequirement | Связь по ID (один ко многим)    | UniversitySession → PreparationRequirement (через сервис) | UniversitySession не содержит полей подготовки.                         |
| UniversitySession    | ScheduleBlock        | Нет прямой связи                | Связь через PreparationRequirement и Task | UniversitySession не знает о запланированных блоках.                    |
| PreparationRequirement | ExecutionRecord     | Один ко многим (одно требование может иметь много записей попыток) | PreparationRequirement → ExecutionRecord | ExecutionRecord не обновляет PreparationRequirement; он является фактическим следствием. |
| PreparationRequirement | ScheduleBlock       | Один ко многим (одно требование может быть выполнено в нескольких блоках) | PreparationRequirement → ScheduleBlock (после планирования) | PreparationRequirement не содержит времени выполнения.                  |
| Task                 | ScheduleBlock        | Один ко многим (одна задача может быть выполнена в нескольких блоках) | Task → ScheduleBlock         | Task не содержит времени выполнения.                                    |
| Task                 | ExecutionRecord      | Один ко многим                  | Task → ExecutionRecord       | ExecutionRecord не обновляет Task.                                      |
| Obsidian             | Personal OS          | Чтение знаний, запись метаданных | OS читает Obsidian для знаний, пишет метаданные в конец заметок | OS не модифицирует пользовательский контент в Obsidian; OS не зависит от структуры заметок для логики. |
| Google Calendar      | Personal OS          | Чтение фикс. обязательств, запись прогнозов | OS читает внешний календарь для фикс. обязательств, пишет блоки подготовки как прогноз | OS не считает внешний календарь источником истины для своих блоков подготовки; OS не пытается двухстороннюю синхронizцию без политики конфликтов. |
| Telegram             | Personal OS          | Приём команд и задач            | Telegram → OS (как вход)     | OS не считает Telegram источником истины для состояния задач; OS не пишет состояние задач обратно в Telegram. |

## Резюм

Соблюдение этих границ гарантирует:
- **Поддерживаемость**: изменения в одном компоненте minimally влияют на другие.
- **Тестируемость**: домен можно тестировать изолированно от инфраструктуры.
- **Гибкость**: легко заменять реализации инфраструктуры (например, переключаться с SQLite на PostgreSQL или с Google Calendar на Exchange).
- **Ясность**: пользователь и разработчики понимают, где происходит что и кто за что отвечает.
- **Соответствие принципам чистой архитектуры**: независимость слоёв, правило зависимости, инверсия зависимости.

Персональная OS следует этим границам, чтобы избежать ловушек "большого комка грязи" и обеспечить долгосрочную жизнеспособность системы.

# Инварианты планировщика Personal OS

Формальное описание правил, которые должен соблюдать детерминированный планировщик при генерации ScheduleBlock из требований (Task, PreparationRequirement) при учете фиксированных обязательств и предпочтений пользователя.

## 1. Основные определения

### Временные интервалы
Время моделируется как 연속ная линейная величина с метрикой, измеряемой в минутах от фиксированной эпохи. Дата-время с timezone преобразуется в это представление для упрощения расчетов.

Любой блок B характеризуется:
- `B.start: ℝ` - время начала (в минутах от эпохи)
- `B.end: ℝ` - время конца (в минутах от эпохи)
- `B.duration = B.end - B.start ≥ 0` - продолжительность

Временные интервалы считаются полузакрытыми [start, end) для упрощения проверки пересечений.

### Множество блоков
Планировщик работает с конечными множествами блоков:
- `R` - множество требований (Task и PreparationRequirement), которые нужно распланировать
- `F` - множество фиксированных обязательств (ScheduleBlock с source ≠ SCHEDULER и locked = true)
- `S` - множество предлагаемых блоков расписания (выход планировщика)
- `B ⊆ S ∪ F` - любое планируемое или фиксированное обязательство

### Типы блоков
Каждый блок имеет тип из набора:
`BlockType = {TASK_WORK, PREPARATION, BUFFER, TRAVEL, BREAK, FIXED_COMMITMENT}`

Каждый блок имеет источник создания:
`BlockSource = {USER, SCHEDULER, AI_SUGGESTION, SYSTEM}`

## 2. Жесткие ограничения (Hard Constraints)

Жесткие ограничения представляют собой логические условия, которые **должны** выполняться для любого допустимого множества блоков B. Нарушение любого жесткого ограничения делает план недопустимым.

### И2.1. Время не может быть отрицательным
∀B ∈ B: B.start ≥ 0 ∧ B.end ≥ B.start

**Пояснение**: Время не может идти назад, и блок не может иметь отрицательную продолжительность.

### И2.2. Отсутствие временных пересечений (непересечение обязательств)
∀B₁, B₂ ∈ B где B₁ ≠ B₂:
either B₁.end ≤ B₂.start or B₂.end ≤ B₁.start

**Эквивалентная форма**: ¬∃B₁,B₂∈B,B₁≠B₂: (B₁.start < B₂.end) ∧ (B₂.start < B₁.end)

**Пояснение**: Два разных блока не могут занимать одно и то же время. Это фундаментальное ограничение невозможности находиться в двух местах одновременно или выполнять две задачи одновременно без явного мультитаскинга (который мы не моделируем как продуктивный).

### И2.3. Блоки Фиксированных Обязательств неизменяемы
∀F ∈ F: ¬∃S ∈ S: (S.source = SCHEDULER) ∧ (F.block_id = S.block_id)

**Более строгая форма**: Если блок имеет source ≠ SCHEDULER, то он не может быть создан или модифицирован планировщикомSource = SCHEDULER.

**Пояснение**: Планировщик может создавать или модифицировать только блоки со sourcesource = SCHEDULER. Блоки, пришедшие от пользователя (USER), системы (SYSTEM) или ИИ-предложений (AI_SUGGESTION) до планирования, должны оставаться неизменными в выходе планировщика (хотя пользователь может لاحقًا изменить их вручную, сделав источник USER).

### И2.4. Блоки подготовки должны предшествовать связанным событиям
∀PR ∈ PreparationRequirements:
let linked_event = get_linked_academic_event(PR)
∃SB ∈ S: (SB.requirement_id = PR.requirement_id) ∧ (SB.end ≤ linked_event.scheduled_occurrence.starts_at)

**Пояснение**: Для каждого требования подготовки должно существовать хотя бы одно запланированное время блока подготовки, которое заканчивается не позже начала связанного академического события. Это гарантирует, что подготовка успевает быть завершенной перед событием.

### И2.5. Время подготовки уважает минимальные требования
∀PR ∈ PreparationRequirements:
∀SB ∈ S: (SB.requirement_id = PR.requirement_id) → (SB.duration ≥ PR.minimum_duration_minutes)

**Пояснение**: Каждый блок подготовки, связанный с требованием, должен иметь продолжительность не меньше минимума, указанного в требовании. Это гарантирует, что даже при фрагментации подготовки на несколько блоков, суммарное время не упадет ниже абсолютного минимума.

### И2.6. Суммарная нагрузка не превышает физические возможности
∀day ∈ Days:
let blocks_in_day = {B ∈ B | B.start < day_end ∧ B.end > day_start}
∑_{B∈blocks_in_day} B.duration ≤ max_daily_capacity(day)

**Где max_daily_capacity(day)** - настраиваемый параметр, представляющий максимальное количество минут, которое пользователь может продуктивно посвятить работе в один день с учетом сна, питания и базовых потребностей.

**Более строгая версия для продуктивной работы**:
∀day ∈ Days:
let productive_blocks = {B ∈ blocks_in_day | B.block_type ∈ {TASK_WORK, PREPARATION}}
∑_{B∈productive_blocks} B.duration ≤ max_productive_capacity(day)

**Пояснение**: Пользователь не может работать бесконечно. Есть физические и когнитивные пределы на количество продуктивной работы в день. Планировщик должен уважать эти пределы.

### И2.7. Требования имеют достаточно времени для выполнения
∀R ∈ Requirements:
let time_allocated = ∑_{SB∈S: SB.links_to(R)} SB.duration
let minimum_required = get_minimum_time_required(R)
time_allocated ≥ minimum_required

**Где LinksTo определяется как**:
- Для Task: SB.task_id = R.task_id
- Для PreparationRequirement: SB.requirement_id = PR.requirement_id

**И get_minimum_time_required вычисляет**:
- Для Task: сумма уверенных оценок от исторических данных или базовое minimum из EffortEstimate
- Для PreparationRequirement: сумма minimum_duration_minutes по всем связанным блокам (чтобы избежать двойного счета при фрагментации)

**Пояснение**: Планировщик должен выделить достаточно суммарного времени для выполнения каждого требования. Это предотвращает ситуацию, когда требование разбивается на множество мелких блоков, суммарная продолжительность которых недостаточна.

### И2.8. Блоки буфера имеют неотрицательную продолжительность
∀B ∈ B: (B.block_type = BUFFER) → (B.duration ≥ 0)

**Пояснение**: Блоки буфера по определению представляют время резерва и не могут иметь отрицательную продолжительность. Нулевая продолжительность допустима (отсутствие буфера).

### И2.9. Блоки путешествия уважают географические ограничения
∀B ∈ B: (B.block_type = TRAVEL) → 
  (B.start ≥ departure_ready_time) ∧ 
  (B.end ≤ arrival_required_time) ∧
  (B.duration ≥ minimum_travel_time(B.from_location, B.to_location, B.time_of_day))

**Где**:
- departure_ready_time = время, когда пользователь готов отправиться (после завершения предыдущей деятельности)
- arrival_required_time = время, когда пользователь должен быть на месте (начало следующей деятельности)
- minimum_travel_time - функция, вычисляющая теоретически возможное минимальное время в пути на основе расстояния, moyena transport и условий (трафик, погода и т.д.)

**Пояснение**: Блок путешествия должен фактически обеспечить перемещение из точки A в точку B. Он не может beginnen раньше, чем пользователь готов отправиться, и должен закончиться не позже времени, когда нужно быть на месте. Плюс продолжительность должна быть достаточной для фактического перемещения.

### И2.10. Время начала не может быть в прошлом для активного планирования
∀B ∈ S: B.start ≥ planning_reference_time

**Где planning_reference_time** - время, относительно которого производится планирование (обычно "сейчас" или начало planning периода).

**Пояснение**: При планировании на будущее планировщик не должен предлагать блоки, которые уже начались в прошлом. Это предотвращает логические противоречия. (Исключение作сана для корректировки текущего выполнения, но это относится к сферу исполнения, не планированию).

## 3. Мягкие ограничения (Soft Constraints)

Мягкие ограничения представляют собой предпочтения, нарушение которых не делает план недопустимым, но уменьшает его качество или пригодность для пользователя. Планировщик пытается максимизировать исполнение мягких ограничений, не нарушая жестких.

Мягкие ограничения могут быть combined в единую функцию качества плана Q(S) которую планировщик стремится максимизировать при условии соблюдения всех жестких ограничений.

### И3.1. Предпочтительное время суток для типа деятельности
Пусть w(t, type) ∈ [0,1] - функция предпочтения времени суток t для типа деятельности type.

Тогда мягкое ограничение:
Maximize ∑_{B∈S} [w(B.start_time_of_day, B.effective_type) × B.duration]

**Где effective_type учитывает контекст**:
- Для BLOCK.block_type = TASK_WORK: effective_type = Task.cognitive_type (из metadata задачи)
- Для BLOCK.block_type = PREPARATION: effective_type = PreparationRequirement.cognitive_type
- Для остальных типов: effective_type = block_type (буфер, дорога и т.д. имеют свои предпочтения)

**Пояснение**: Планировщик должен стараться расположить блоки умственной работы в часы высокой концентрации пользователя, рутинную работу в часы меньшей концентрации и т.д. Функция w получена из исторических данных или прямых предпочтений пользователя.

### И3.2. Предпочтительная продолжительность блоков
Пусть preferred_duration(type) - предпочтительная продолжительность блока типа type (из исторических данных или предпочтений пользователя).
Пусть penalty(duration, preferred) = |duration - preferred| / max(duration, preferred) - нормализованная штраф-функция.

Тогда мягкое ограничение:
Minimize ∑_{B∈S} [penalty(B.duration, preferred_duration(B.effective_type)) × weight(B)]

**Где weight(B)** - вес блока, отражающий важность соблюдения предпочтительной продолжительности для этого типа работы (более высокая для сложной умственной работы, ниже для буферного времени).

**Пояснение**: Пользователь часто имеет интуитивное предпочтение определенной длительности рабочих блоков (например, техника Pomodoro предполагает 25 минут). Планировщик должен уважать эти предпочтения там, где это возможно без нарушения жестких ограничений.

### И3.3. Минимизация переключения контекста
Пусть transition_cost(type₁, type₂) ≥ 0 - стоимость переключения от типа деятельности type₁ к типу type₂.
Стоимость симметрична: transition_cost(type₁, type₂) = transition_cost(type₂, type₁)
И transition_cost(type, type) = 0 (нет стоимости при том же типе).

Тогда мягкое ограничение:
Minimize ∑_{i=1}^{n-1} transition_cost(block_i.effective_type, block_{i+1}.effective_type)
**Где блоки отсортированы по времени**: block₁.start ≤ block₂.start ≤ ... ≤ blockₙ.start

**Пояснение**: Переключение между разными типами деятельности требует когнитивных ресурсов и времени на адаптацию. Планировщик должен стараться группировать похожие виды деятельности вместе чтобы снизить суммарные издержки переключения.

### И3.4. Минимизация путешествий
Пусть travel_distance(B) - фактическое расстояние, которое нужно преодолеть для блока путешествия B (вычисляется из location полей связанных событий).
Пусть travel_penalty(distance) = distance / max_reasonable_distance - нормализованная штраф-функция.

Тогда мягкое ограничение:
Minimize ∑_{B∈S: B.block_type = TRAVEL} [travel_penalty(travel_distance(B))]

**Альтернативная форма на основе времени**:
Minimize ∑_{B∈S: B.block_type = TRAVEL} [B.duration - minimum_possible_travel_time(B.from, B.to, B.time)] 

**Пояснение**: Путешествие потребляет время и энергию без прямой продуктивной выгоды (в контексте образовательной/рабочей деятельности). Планировщик должен стараться минимизировать суммарное время в пути.

### И3.5. Соблюдение предпочтительных окон для требований
Пусть PreparationRequirement имеет множество предпочтительных окон PreferredWindows = {W₁, W₂, ..., Wₖ} где каждый Wᵢ = [Wᵢ.start, Wᵢ.end] с уровнем предпочтительности wᵢ ∈ [0,1].

Для каждого распределенного блока подготовки SB связанного с требованием PR:
пусть overlap_fraction = 측정_перепрыты([SB.start, SB.end], PreferredWindows) / SB.duration
где measurement возвращает долю времени блока, попадающую в любое из предпочтительных окон.

Тогда мягкое ограничение:
Maximize ∑_{PR∈PreparationRequirements} ∑_{SB∈S: SB.links_to(PR)} [overlap_fraction(SB, PR.PreferredWindows) × SB.duration × PR.priority_weight]

**Где priority_weight отражает важность соблюдения предпочтительных окон для этого требования** (высокий для критической подготовки, низкий для опциональной).

**Пояснение**: Некоторые виды подготовки лучше выполнять в определенное время (например, чтение сложного материала утром, когда ум свеж). Планировщик должен уважать эти предпочтения там, где это возможно.

### И3.6. Баланс типов деятельности в течение дня
Пусть ideal_daily_distribution: BlockType → [0,1] - идеальная доля каждого типа деятельности в течение дня (сумма по всем типам = 1).
Пусть actual_fraction(Btype, day) = (∑_{B∈S: B.block_type=Btype ∧ B∈day} B.duration) / (∑_{B∈S: B∈day} B.duration) - фактическая доля типа Btype в день.

Тогда мягкое ограничение:
Minimize ∑_{day∈Days} ∑_{Btype∈BlockType} |actual_fraction(Btype, day) - ideal_daily_distribution(Btype)|

**Пояснение**: Пользователь может иметь идеи о том, как должно распределяться его время между разными видами деятельности (например, 50% учёба, 30% работа, 20% отдых). Планировщик должен стремиться к этому распределению, уважая жесткие ограничения.

### И3.7. Соблюдение уровней энергии
Пусть energy_level(t) ∈ [0,1] - моделированный или измеренный уровень энергии пользователя в момент времени t.
Пусть cognitive_demand(type) ∈ [0,1] - когнитивная нагрузка типа деятельности type (0 = рутинная, 1 = высокая сосредоточенная работа).

Тогда мягкое ограничение:
Maximize ∑_{B∈S} [energy_level(B.start_time) × (1 - cognitive_demand(B.effective_type)) × B.duration]
**Эквивалентно минимизации несоответствия**:
Minimize ∑_{B∈S} [|energy_level(B.start_time) - cognitive_demand(B.effective_type)| × B.duration]

**Пояснение**: Сложную когнитивную работу лучше выполнять когда уровень энергии высок, а рутинную работу можно выполнять когда уровень энергии ниже. Планировщик должен согласовывать сложность работы с доступной энергией.

## 4. Вывод планировщика: Критерии оптимальности

Планировщик ищет множество блоков S* такое что:
1. S* удовлетворяет всем жестким ограничениям (И2.1-И2.10)
2. Среди всех множеств, удовлетворяющих жестким ограничениям, S* максимизирует агрегированную функцию качества:
   
   Q(S) = α₁·Q₃.₁(S) + α₂·Q₃.₂(S) + α₃·Q₃.₃(S) + α₄·Q₃.₄(S) + α₅·Q₃.₅(S) + α₆·Q₃.₆(S) + α₇·Q₃.₇(S)
   
   Где Q₃.ᵢ - вклад мягкого ограничения i в качество плана (нормализованный к [0,1]), а αᵢ - веса важности соответствующих предпочтений (αᵢ ≥ 0, ∑αᵢ = 1).

**Особый случай**: Если ∃Sᵢ удовлетворяющее &&Q(S₁) > Q(S₂)&& для всех допустимых S₂, то Sᵢ является единственным оптимальным решением.
Если множество решений имеет одинаковое максимальное Q(S), планировщик применяет tie-breaking правила:
1. Минимизировать количество фрагментации требований (предпочитать меньше блоков на требование)
2. Минимизировать суммарное количество блоков (простota принципа)
3. Лексикографический порядок по времени начала блоков (расписание которое начинается раньше предпочтительнее)

## 5. Специальные случаи и граничные условия

### 5.1. Требование с нулевой минимальной продолжительностью
Если PR.minimum_duration_minutes = 0:
- И2.5 автоматически выполняется для любого блока подготовки связанного с PR
- Planning фокусируется на выполнении других ограничений и предпочтений

### 5.2. Требование без предпочтительных окон
Если PR.PreferredWindows = ∅:
- И3.5 не вносит вклад в качество плана для этого требования
- Планировщик свободен расположить блок подготовки в любое удобное время, уважая другие ограничения

### 5.3. Полностью фиксированное расписание
Если F уже заполняет все доступное время уважая И2.2:
- Единственное допустимое S = ∅ (пустое множество)
- Планировщик возвращает пустой набор новых блоков
- Сигнализирует пользователю о отсутствии свободного времени для новых требований

### 5.4. Нестираемое требование
Если существует требование R такое что:
∀S: удовлетворяющее жестким ограничениям → time_allocated_for(R) < minimum_required(R)
Тогда:
- Планировщик должен вернуть специальный код ошибки UNSATISFIABLE_REQUIREMENT
- Указать конкретное требование R и deficit = minimum_required(R) - max_possible_time_allocation
- Позволяет пользователю либо уменьшить требование, либо освободив время через удаление/перенос фиксированных обязательств

### 5.5. Враждебные фиксированные обязательства
Если F само по себе нарушает И2.2 (внутри F есть пересекающиеся блоки):
- Планировщик должен вернуть код ошибки INCONSISTENT_FIXED_COMMITMENTS
- Указать конкретные конфликтующие блоки Fᵢ, Fⱼ
- Это указывает на проблему во входных данных, которую нужно решить на уровне пользователя или источника данных

## 6. Детерминированность

Планировщик должен быть детерминированным:
∀R₁,R₂,F₁,F₂: 
  (R₁ = R₂) ∧ (F₁ = F₂) → 
  planner(R₁, F₁) = planner(R₂, F₂)

**Где planner(R, F)** возвращает либо:
- Набор блоков S удовлетворяющий критериям оптимальности (раздел 4), либо
- Ошибку из специальных случаев (раздел 5)

Это достигается через:
1. Фиксированный порядок обработки требований и фиксированных обязательств
2. Детерминированные алгоритмы решения ограничений и оптимизации
3. Фиксированные правила tie-breaking (раздел 4)
4. Отсутствие случайных или временно-зависимых факторов

## 7. Связь с доменной моделью

Все понятия в этих инвариантах отображаются на сущности доменной модели:
- Requirements R ↔ {Task} ∪ {PreparationRequirement}
- Fixed Commitments F ↔ {ScheduleBlock | source ≠ SCHEDULER}
- Output S ↔ {ScheduleBlock | source = SCHEDULER}
- Block properties map directly to ScheduleBlock.attributes
- Time values map to DateTime fields после преобразования в линейную шкалу
- Типы требований и блоков используют соответствующие перечисления из доменной модели
- Источники блоков используют BlockSource из доменной модели
- Временные окна и preferences используют сущности и value objects из доменной модели

Инварианты формулируются в терминах абстрактных временных интервалов для независимости от конкретной реализации времени, но прямо отображаются на атрибутах ScheduleBlock и связанных сущностей при реализации.

## 8. История изменений и обоснование решений

### Отказ от мягких ограничений как рекомендаций
Первоначально рассматривалось представление мягких ограничений как рекомендаций, которые пользователь может игнорировать. Однако был выбран подход моделирования их как целевой функции для оптимизации потому что:
- Позволяет планировщику автоматически балансировать конкурирующие предпочтения
- Делает поведение планировщика предсказуемым и воспроизводимым
- Устраняет необходимость пользователя постоянно корректировать выход планировщика
- Предоставляет количественную меру качества планов для обучения и улучшения

### Выбор линейной временной шкалы
Время моделируется как линейная величина вместо работы с календарными структурами напрямую потому что:
- Значительно упрощает проверку пересечений и вычисления интервалов
- Позволяет легко работать с относительными времени (например, "за 2 часа до события")
- Избегает сложностей с часовыми поясами, переходом на летнее время и т.д. в логике планирования
- Сохраняет pełną информацию через преобразование назад в календарное время для представления пользователю

### Реальные числа vs целые для времени
Время моделируется как вещественные числа (ℝ) вместо целых минут потому что:
- Позволяет моделировать временные интервалы с произвольной точностью
- Убирает артефакты округления при преобразовании между единицами времени
- Соответствует непрерывному характеру реального времени
- На практике реализация может использовать фикс. точку с достаточной точностью (микросекунды) для всех образовательных/рабочих сценариев

### Явное моделирование переходных издержек
Включение стоимости переключения контекста как мягкого ограничения основано на когнитивных исследованиях показывающих значительные издержки при переключении между разными типами деятельности. Это важно потому что:
- Без учета этих издержек планировщик может создавать фрагментированные расписанияющие снижение продуктивности
- Пользователь часто осознает эти издержки интуитивно и предпочитает group похожие задачи
- Позволяет планировщику рекомендовать структуры дня согласующиеся с естественными ритмами пользователя

### Приоритизация жестких над мягкими ограничениями
Жесткие ограничения представляют неотъемлемые физические и логические ограничения возможности человека.
Мягкие ограничения представляют предпочтения и комфорт.
Приоритизация жестких над мягкими необходима потому что:
- Нарушение жестких ограничений приводит к логически невозможным или вредным планам
- Нарушение мягких ограничений приводит лишь к suboptimal но всё еще выполнимым планам
- Эта иерархия гарантирует, что планировщик никогда не выдаст план который пользователь физически не может выполнить
